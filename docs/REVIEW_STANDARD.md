# 場景審查標準（v0.1，2026-10-22）

> 這份文件記錄 2026-10-21 審查 S001–S050 時實際用的檢查項目和判定方式（結果見 [review_S001-S050.md](review_S001-S050.md)）。
> 目前是「記錄現況」的版本，之後會再統一成正式標準（v1.0），屆時寫進 `CLAUDE.md` 的每場景流程。
> 每個檢查項目有編號（M = 機械檢查、C = 內容檢查），修正紀錄和 commit 訊息可以直接引用編號。

---

## 一、審查流程

1. **機械檢查**：用腳本掃描全部場景（M1–M8），不需要執行程式。
2. **重跑**：在獨立的 git worktree 重跑每支程式，避免覆蓋主目錄的輸出。指令：
   ```bash
   PYTHONIOENCODING=utf-8 "C:/Users/user/anaconda3/envs/drones/python.exe" -u src/<domain>/<script>.py
   ```
   不用 `conda run`（在 Windows 背景執行會卡住）。
3. **內容檢查**：逐項比對 README、場景卡片、程式碼和實際輸出（C1–C10）。
4. **複核**：嚴重問題（HIGH）至少抽查一部分，由另一個人（或另一個 session）親自看程式碼確認，不能只信單一審查者的回報。
5. **落檔**：結果寫進 `docs/review_*.md`，每個問題標嚴重度、類型、檔案和行號。

---

## 二、機械檢查（M）

| 編號 | 檢查項目 | 通過條件 |
|---|---|---|
| M1 | 檔案齊全 | 卡片、`.py`、`outputs/<domain>/<script名>/` 各一個；輸出資料夾裡至少一張 PNG、一個 GIF、一份 README.md |
| M2 | 命名一致 | 輸出資料夾名稱 = 腳本檔名（不含 `.py`）；腳本裡寫的輸出路徑和實際資料夾相同 |
| M3 | 必要函式 | 腳本有 `run_simulation()`、至少一個 `plot_*()`、`save_animation()` |
| M4 | 無頭繪圖 | 腳本開頭有 `matplotlib.use('Agg')` |
| M5 | 狀態一致 | 卡片 Status、`PROGRESS.md` 勾選、`PROGRESS.md` 統計表、根目錄 `README.md` 統計表四者一致 |
| M6 | 連結有效 | outputs README 裡每個相對連結都指得到檔案（圖片、場景卡片、其他文件） |
| M7 | 連結內容正確 | 連結文字寫的場景名稱，和目標卡片的實際標題一致（不能只是編號對、名稱錯） |
| M8 | 輸出都有被引用 | 輸出資料夾裡每張圖、每個 GIF 都在 README 裡出現；沒有被引用的就是多餘或過期的檔案 |

## 三、內容檢查（C）

| 編號 | 檢查項目 | 通過條件 |
|---|---|---|
| C1 | 能跑完 | 程式結束代碼為 0，沒有例外 |
| C2 | 執行時間 | 單一腳本 10 分鐘內跑完（含 GIF）。超過就降低蒙地卡羅次數或 GIF 幀數 |
| C3 | 結果一致 | README 裡每個數字（結果表、Key findings、內文）都和重跑的實際輸出一致，只容許四捨五入差異 |
| C4 | 參數一致 | README「Key Parameters」每一列都和程式實際使用的常數一致 |
| C5 | 卡片偏離有說明 | 程式和卡片的參數、方法、策略不同時，README 必須寫明改了什麼、為什麼改；卡片要求的策略沒做也要說明 |
| C6 | 可重現 | 所有隨機來源都有固定種子（包括重採樣、蒙地卡羅、動畫重新模擬）；同一支程式跑兩次結果相同 |
| C7 | 程式正確 | 公式、符號、單位、座標方向和卡片的數學模型一致；宣稱有用到的函式真的有被呼叫；沒有差一步、重複計算等錯誤 |
| C8 | 比較有鑑別力 | 被比較的策略在設計上確實不同，結果差異來自方法本身，而不是程式設定（例如不公平的速度上限、同一段程式碼、測不出差別的指標、根本不會觸發的機制） |
| C9 | 結論有根據 | README 的每個解釋和結論都能從程式行為或輸出數據得到；不能把 bug 或設定造成的結果解釋成方法的特性 |
| C10 | 物理合理 | 數值的量級合理（例如能耗、航程、速度、時間）；用「單價 × 數量」重算關鍵數字，沒有差一個數量級 |

## 四、嚴重度

| 等級 | 定義 | 例子 |
|---|---|---|
| **HIGH** | 程式錯誤造成結果或結論錯；README 數字或結論和實際不符；比較在設計上無效 | 符號寫反、結果表過期、兩個策略是同一段程式碼 |
| **MED** | 參數表不符；卡片偏離沒說明；指標定義有瑕疵但不推翻結論 | 參數表寫 10 m/s、程式是 8 m/s |
| **LOW** | 小瑕疵，不影響結論 | 顏色描述錯、百分比差 1%、docstring 過期 |

---

## 五、問題類型（決定修法）

| 類型 | 說明 | 修法 |
|---|---|---|
| A. 程式錯誤 | 公式、符號、單位錯，結論跟著錯 | 改程式 → 重跑 → 重寫 README 結果和結論 |
| B. 比較無鑑別力 | 策略在設計上必然相同，或條件不公平 | 重新設計情境，必要時修改卡片並在 README 說明 |
| C. README 過期或描述錯 | 程式改過但 README 沒更新，或解釋和程式行為不符 | 重跑 → 重寫 README |
| D. 參數表不符 | 只有文件和程式常數對不上 | 只改文件 |

## 六、修正後的驗收

一個場景要同時滿足以下條件才算修好：
1. M1–M8、C1–C10 全部通過（輕微問題也要修）。
2. README 的結果數字是**這次重跑**的輸出，不是手抄或沿用舊值。
3. 由沒有參與修改的審查者（另一個 agent 或 session）重跑並核對 C3、C4、C7、C8，確認通過。
4. 一個場景一個 commit，訊息格式：`Fix S0xx <scenario name>: <主要修正>`。
